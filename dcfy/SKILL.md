# dcfy (구 decisionfy) — 미결 결정을 문서로 모아 고르면 프롬프트가 복사되게

## 0. 누가 쓰는가
- 접수 비서는 직접 작성하지 않는다. 비서는 **수집 근거만 모아** 하위 에이전트(Agent 도구, 문서 실행 역할)에 `ai-agency/templates/agent-handoff.md` 양식으로 위임한다.
- 인계에 반드시: 작업 ID(`ai-agency/docs/code-ticket-policy.md` 형식), 아래 1단계의 원천 목록(프로젝트·파일 경로·대화에서 나온 결정과 비서 추천), 이미 답한 결정 제외 근거(사용자 원문), 2~6단계와 완료 조건, 보고 양식(`templates/agent-report.md`).
- 실행 에이전트가 2~6단계를 수행하고 부모에게만 보고한다.

## 1. 결정 수집 (비서)
원천 — 빠짐없이 훑되 프로젝트 사실은 원본에서만 가져온다:
1. 현재 대화의 미결 질문·승인 대기(도구 권한, 배포 방법, 외부 게시 등).
2. 각 프로젝트 저장소(`ai-agency/config/projects.json`의 `path`)의 `STATUS.md` "사용자 결정 대기", 결정 기록(`docs/decisions/` 등), 정책서·스펙의 "사용자 결정 필요" 표.
3. 하위 에이전트 보고의 "사용자 판단 필요".
4. **이전 응답 기록** `ai-agency/docs/reports/decisions/*-response.md`(최신부터)와 **이전 결정 json의 `resolution`**. `resolution`이 있는 ID는 다시 올리지 않는다. 단 `status`가 `deferred`(보류)·`blocked`(차단)이면 원본에서 최신 상태를 확인해 다시 올린다(이전 응답 원문·남은 일을 "참고"에 적는다). resolution이 없는 옛 문서는 응답 원문에서 답한 ID는 원본 반영을 확인하고 빼고, "보류"·"미결"·"다음 결정 문서로 이월" ID는 원본에서 최신 상태를 다시 확인해 올린다(보류는 사용자 메모와 준비된 [제안]을 "참고"에 함께 적는다).

- **이미 사용자가 답한 것은 제외**한다(근거: 사용자 원문·날짜). 애매하면 넣고 "참고"에 이전 답을 적는다.
- 결정이 아닌 사용자 할 일(검수, 로그인, 확인 등)은 `todos`로 따로 둔다. 사용자가 바로 따라 할 수 있게 원본 근거로 무엇을·왜·어디서·단계별 방법·완료 기준·예상 소요·회신 문구·주의를 상세 필드(`references/schema.md` todos[] 상세 필드)로 풀어 쓴다(2026-11-18 사용자 요청 "사용자 할 일 더 자세히 안내").
- `~/yeonpm/deprecated` 하위는 쓰지 않는다. 비밀값·개인정보는 넣지 않는다.

## 2. decisions.json 작성 (실행 에이전트)
- 스키마와 예시: `references/schema.md`, `references/example-decisions.json`.
- 항목마다: 결정 ID, 프로젝트, 제목, 배경(왜 필요한지), 막는 것, 선택지(설명 `desc`, 장점 `pros`·단점 `cons`·고려할 점 `considerations`), 추천안(`recommended` + 이유 한 줄), 긴급도, 원본 경로·링크. '보류'·'직접 입력'·메모 칸은 템플릿이 자동으로 붙인다.
- **선택지 설명 규칙**(사용자 지시 2026-11-17 "앞으로 각 결정 사안에 설명이 있으면 좋을만한 선지에는 설명을 넣어줘. 장단점이나 생각해볼점, 고려할부분등"): 설명이 도움이 되는 선택지 — 명백하지 않은 것, 트레이드오프가 있는 것, 되돌리기 어려운 것 — 에는 장점·단점·고려할 점을 **각 1~3줄**로 넣는다. "예/아니오"처럼 자명한 선택지는 생략 가능. 추천안에는 최소 하나를 넣는다(없으면 build가 경고). 내용은 원본(정책서의 세부 규칙·근거·대안 칸, 스펙 이유, STATUS 위험, 조사 비교표)에서 가져오고 줄 끝에 근거를 괄호로 적는다 예 `(S-2)`. 원본에 없으면 일반적 고려사항만 줄 앞에 `(비서 정리)`를 붙여 쓰고, 추정이면 `추정`이라고 쓴다. 보고에 `(비서 정리)`로 채운 선택지 수를 적는다.
- 질문·선택지는 **원본 문구를 그대로** 옮긴다. 추정 금지. 원본을 못 찾으면 `note`에 "원본 확인 필요"를 적고 보고에 남긴다. 원본에 추천이 없으면 추천을 만들지 말고 `note`에 "원본에 추천 없음". 비서 대화에서 나온 추천은 이유에 "(비서 정리)"를 붙이고 sources에 대화 근거를 적는다.
- 문항이 여러 개인 결정(정책 Q-1~Q-8 등)은 문항별 항목으로 나누고 `group`으로 묶는다. 피드백형은 `type: "text"` + `fields`.
- **약어 풀어 쓰기**(사용자 메모 2026-11-26 "D28이 뭔지 내가 어떻게 알아. 이 사안 보완해서 다시 올려줘."): 결정 항목의 제목·배경·선택지에 내부 약어·코드(D28, B10, U3, IARC 등)를 쓸 때는 처음 나올 때 쉬운 말로 풀어 쓴다(예: D28 = 베타 시작 후 28일째). 사용자가 원본 문서를 보지 않고도 이해할 수 있게 쓴다.
- 저장 위치: 여러 프로젝트에 걸친 결정 모음이므로 `/Users/you/yeonpm/ai-agency/docs/reports/decisions/YYYY-MM-DD-HHMM-decisions.json`(KST). 원본은 각 프로젝트에 남고 여기는 링크만 둔다. 한 프로젝트만이면 그 저장소 `docs/reports/decisions/`에 둬도 된다(허브가 서빙하는 docs/ 아래).

## 3. HTML 생성 — 손으로 짜지 않는다
```bash
source ~/.nvm/nvm.sh >/dev/null && nvm use 24 >/dev/null
node ~/.claude/skills/dcfy/scripts/build.cjs <...-decisions.json>   # 같은 이름 .html 생성
```
- 스키마 점검 실패 시 메시지대로 JSON을 고친다. 원본 경로가 등록 프로젝트의 docs/·knowledge/·STATUS.md·README.md면 허브 링크가 자동으로 붙는다. 출력 JSON의 `hubUrl`이 문서 주소다.
- 생성 문서 동작(템플릿 `assets/template.html` 고정): 핵심 요약(총 n건·긴급 n건·응답 수·프로젝트별 수, 확정 항목이 있으면 확정 n건(완료·진행)·미결 n건) → 사용자 할 일 → 프로젝트별 카드(라디오/체크/텍스트, 직접 입력, 보류, 메모). 하단 고정 '프롬프트'가 선택에 따라 실시간 작성되고, 선택 변경은 즉시·텍스트는 입력 멈춘 뒤 300ms에 `navigator.clipboard.writeText`로 복사(실패 시 숨은 textarea + `execCommand('copy')` 폴백), 성공/실패 토스트. 수동 '복사', '추천안 일괄 선택', '초기화' 버튼, localStorage로 선택 유지. htmlfy 규칙(한국어, 인라인 CSS/JS, 외부 요청 0, 다크모드, favicon data URI, 하단 작성일·작업 ID)을 템플릿이 지킨다.
- 프롬프트 패널은 기본 접힘(사용자 지시 2026-11-26): 접힌 한 줄 바에 응답·미결 건수, '복사', '펼치기'만 보이고, 펼침 상태는 사용자가 펼쳤을 때만 localStorage에 저장(값 없으면 항상 접힘). 접혀 있어도 프롬프트 갱신·자동 복사·토스트는 동작한다.
- '직접 입력'은 그 선택지 카드 안에 입력칸이 있다(사용자 지시 2026-11-26): 마우스·터치로 고르면 입력칸에 바로 포커스, 입력칸을 누르거나 타이핑하면 자동 선택, 다른 선택지로 바꾸면 값은 남고 프롬프트에서는 빠지며 다시 고르면 복원. 키보드(화살표·Space)로 고를 땐 포커스를 옮기지 않고 Tab으로 입력칸에 간다(화살표 이동이 막히지 않게).
- 카드의 '배경'(파랑)·'막는 것'(주황)·'참고'(보라) 레이블은 색 다른 둥근 테두리 칩이며 본문은 칩 옆에 둔다(사용자 지시 2026-11-26, 확정 카드 동일, 라이트·다크 토큰, 390px 줄바꿈 자연스럽게).
- `resolution`이 있는 항목(7단계)은 **읽기 전용 확정 카드**: 입력 없음, "확정"·상태 배지(조치 대기/진행 중/완료/차단/보류), 확정한 답·지시 요약·사용자 지시 원문(인용)·조치·구현 기록(날짜·담당·증거)·결과·남은 일. 프롬프트(미결 줄 포함)·클립보드·추천안 일괄·초기화·localStorage 복원에서 빠진다. 보류는 "다음 결정 문서로 이월" 표시. 증거가 허브 서빙 경로면 링크, 커밋 SHA·작업 ID는 텍스트.
- 프롬프트 형식: 첫 줄 `결정 문서 <날짜> 응답`, 둘째 줄 문서 경로·작업 ID, 이어 `[ID] 프로젝트·제목 → 선택: … / 메모: …`(추천안을 고르면 "(추천안)"), 고르지 않은 항목은 `미결 n건: [ID], …` 한 줄, 끝에 위임 요청 한 줄.

## 4. 검증
```bash
node ~/.claude/skills/htmlfy/scripts/verify.cjs <문서.html> <같은폴더>/<같은이름>.png   # 콘솔 오류 0, 외부 요청 0, 가로 넘침 0
node ~/.claude/skills/dcfy/scripts/test-clipboard.cjs "<허브 URL>"                  # 클립보드 = 프롬프트 (기본 접힘·펼치기 후 프롬프트 표시 포함 모든 단계 ok)
```
- 클립보드는 보안 컨텍스트(허브 http://127.0.0.1)에서 동작한다. 테스트는 헤드리스 새 프로필에서 라디오·메모(디바운스)·체크박스·추천안 일괄·새로고침 유지·execCommand 폴백을 확인한다. 허브가 꺼져 있으면 htmlfy 5단계대로 켠다.
- 스크린샷을 눈으로 한 번 본다(하단 패널이 내용을 가리지 않는지).

## 5. 로컬 커밋 · 띄우기
- 해당 저장소에 html + json + png만 스테이징해 커밋: `[작업ID] docs: <요약>` + 빈 줄 + `Co-Authored-By:` 줄. 커밋 후 묻지 않고 원격 브랜치로 **push한다**(SEC-AGENCY-RULES-0020, force 금지).
- `open -a "Google Chrome" "<허브 URL>"` 로 사용자 크롬에 띄운다(file://로 열지 않는다 — 클립보드·링크가 허브 기준).

## 6. 보고 (부모에게, templates/agent-report.md)
- 문서 경로·허브 URL·스크린샷 경로, 항목 수(프로젝트별·긴급), 원본을 못 찾은 항목, 원본에 추천이 없던 항목, 검증 수치, 커밋 저장소·짧은 SHA·push 여부, 확인 못 한 것.
- 비서는 사용자에게 "문서에서 고르면 프롬프트가 복사되니 대화창에 붙여 넣으라"고 안내한다. 붙여 넣은 응답이 오면 7단계로 처리한다.

## 7. 응답 처리와 확정 기록 (2026-11-20 추가)
근거: 사용자 지시 2026-11-20 "앞으로 decisionfy로 문서로부터 내가 결정한 것들은 프롬프트 전달받은 뒤에 내 지시를 해당 문서에도 readonly로 확정하고, 어떻게 조치/구현했는지도 결과로 기록해놔줘."

비서가 사용자 응답 프롬프트를 받으면 처리 에이전트(하위 에이전트)에 위임하고, 처리 에이전트가 다음을 한다.
1. 응답 원문을 같은 폴더 `<문서 이름>-response.md`에 저장한다(응답 원문·미결 ID 목록·처리 결과·이월 목록).
2. 답한 ID마다 그 문서 json에 `resolution`(`references/schema.md`)을 채운다. `status`는 결정이면 `decided`, 보류면 `deferred`. `user_answer`는 프롬프트의 그 항목 줄을 **원문 그대로**(선택·메모 포함, 고치지 않음), `instruction`은 원문과 다르게 해석하지 않은 한 줄 요약, `decided_at`(KST), `response_doc`(1의 경로). 미결(응답 없음) ID는 건드리지 않는다.
3. 같은 json으로 다시 빌드(3단계) → 검증(4단계) → html·json·png·response.md를 커밋(5단계, 커밋 후 push). 같은 문서 URL이 항상 최신 상태를 보여 준다(파일 이름을 바꾸지 않는다).
4. 비서가 각 결정을 담당 역할·작업에 위임한다.
5. 조치가 끝날 때마다 해당 항목의 `actions[]`(날짜·무엇·담당 역할·증거: 커밋 SHA·파일 경로·URL·작업 ID), `result`, `status`(`in_progress`/`done`/`blocked`), `remaining`을 갱신하고 다시 빌드·검증·커밋한다.

- 확정 기록은 사용자 원문 그대로 남긴다. 추정 결과를 쓰지 않는다. 검증하지 않은 조치·결과는 "미검증"이라고 적는다(QA 통과 전 `done` 금지).
- 다음 결정 문서를 만들 때 `resolution`이 있는 ID는 다시 올리지 않는다. `deferred`·`blocked`는 최신 상태를 확인해 다시 올린다(1단계 4번).
- 다시 빌드하면 미결 항목의 동작·프롬프트는 그대로이고, 사용자가 이 브라우저에 남긴 확정 항목의 옛 선택은 복원하지 않고 지운다.
